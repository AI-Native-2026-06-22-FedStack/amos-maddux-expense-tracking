Context
Why This Deliverable
You are continuing on the ExpenseFlow Corporate team building the Expense Tracking & Automatic Deduction Identification capstone. Modules 1–4 gave ExpenseFlow a secure, polyglot backend — the Express Core Case Service (apps/api), the FastAPI engine (services/compute), Postgres, DynamoDB, and Redis — but that backend has no face. Every demo so far has been curl and test output. This is the opening of Sprint 3, the dedicated UI week: the frozen backend gets a Vite + React 18 + strict-TypeScript single-page app, and this deliverable lays its foundation.

Everything in that SPA is built from components, so before hooks, data, routing, or forms, you need the core model right: a component is a function of its props that returns markup, screens are composed from small components, and every prop is precisely typed with no any. In this deliverable you create the apps/web subtree inside your existing monorepo, decompose ExpenseFlow’s provided wireframe into a typed component library — the shared buttons, status/overdue badges, the six-stage expense-case stepper, and a role-aware sidebar — and prove each behaves correctly with behavioral tests. Get this foundation right and the rest of the UI week is tractable; get it wrong and you end up rewriting screens. Deliverable 2 will give these presentational components their logic (hooks), and Deliverable 4 will reuse the atoms inside forms, tables, and dashboards — so today’s library is what the whole SPA rides on.

Objective & Project Scenario
ExpenseFlow’s operators live in a Finance Dashboard, an Expense Reports list, an Approval Queue, and more; employees see My Submissions, Submit Expense, and Log Mileage. Rather than build one sprawling screen component, the team builds the presentational pieces first — a Button, a status/overdue Badge, the six-stage stepper that tracks a case through its lifecycle, and the sidebar that shows entries by role — each a pure function of its typed props, composed into the app shell. No data fetching yet; just the shapes the wireframe shows.

In this deliverable you will scaffold apps/web as a Vite + React 18 + strict-TypeScript project in a design-system layout (atoms/, components/, screens/), port the provided wireframe’s semantic CSS and -- design tokens into CSS Modules, and record ADR-0011 for the styling strategy. You will then decompose the wireframe into a typed component tree and build ExpenseFlow’s shared atoms as pure functions of typed props — a discriminated-union variant for the badge, no any anywhere in props, and one generic reusable component — plus the role-aware sidebar that shows or hides entries by role. Finally you will prove behavior with at least eight Vitest + React Testing Library tests that query by role, label, and text and cover each component’s real states (default, disabled, error), with no snapshot tests. Every artifact transfers straight into the capstone.

Before You Write Code
A component library is the worst place to trust a green happy-path render. A component that renders once can still hide a prop typed any that silently accepts { state: "submitted" } where the code reads status — a blank badge found in the demo, not the editor. A "flexible" component reached for with React.FC<any> defeats the whole point of typing props. A snapshot test passes the moment it is written and catches nothing afterward. The design choices here — how you decompose the wireframe, which prop is a discriminated union, where the generic lives, what states each test covers — are exactly what a closed-book check will ask you to defend. Drive Codex to propose each piece, then verify it yourself by trying to break it: pass a wrong status and watch the compiler, change markup without changing behavior and watch the tests, grep the props for any. The compiler error and the surviving test, not Codex’s "looks right," are the judge.
